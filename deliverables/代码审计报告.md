## 一、P0 致命问题（必须立即修复）

### P0-1 JWT 密钥硬编码默认值，可伪造任意身份 token

**文件**：`backend/src/config/app.config.ts:98`
**级别**：P0（认证体系失守）

```typescript
jwtSecret: process.env.JWT_SECRET || 'dev-secret-change-me-in-production',
```

未配置 `JWT_SECRET` 时静默使用源码中公开的字符串。攻击者可用此密钥为任意 `super` 角色签发合法 JWT，瞬间获得平台超管权限。

**修复**：非 localMode 启动时校验 JWT_SECRET，缺失或等于默认值直接 refuse to start。

---

### P0-2 微信 code2session mock 模式可绕过整个员工认证

**文件**：`backend/src/modules/auth/auth.service.ts:136-153`

未配置微信 appId/appSecret 时不报错而静默降级为 mock openid。攻击者只需知道员工手机号即可登录绑定。

**修复**：非 localMode 下拒绝 mock 模式，启动时校验微信配置必填。

---

### P0-3 ALLOW_LEGACY_DEVICE_TOKEN 在本地模式默认开启，且 legacy 密钥硬编码

**文件**：`backend/src/config/app.config.ts:118-120` + `verify.service.ts:101`

默认值 `'legacy-device-token'` 写在源码中，任何人都能用这把钥匙调用 `/api/device/verify` 绕过一机一密钥体系。

**修复**：默认值改为空字符串；非 localMode 强制 `allowLegacyDeviceToken=false`。

---

### P0-4 核销多步操作无数据库事务，进程崩溃导致数据不一致

**文件**：`backend/src/modules/verify/verify.service.ts:237-331`

5 个 DB 写操作（扣公司额度、扣员工额度、写消费记录、改 QR 状态、改设备时间）全无事务包裹。进程在步骤 4 后崩溃 → 公司已扣、无消费记录、QR 仍有效 → 账目黑洞 + 可重放。

**修复**：用 `DataSource.transaction(async (manager) => {...})` 包裹步骤 2-5。

---

### P0-5 补偿回滚操作未包裹 try-catch，回滚失败导致永久额度泄漏

**文件**：`backend/src/modules/verify/verify.service.ts:266-271, 306-318`

如果回滚的 DB 操作本身失败（连接断/死锁），原始错误被回滚异常覆盖，公司额度已扣但无消费记录——永久蒸发。

**修复**：补偿操作独立 try-catch，无论补偿成功失败都抛原始业务异常，补偿失败时打 error + 告警。

---

### P0-6 CORS 配置 `origin: true` + `credentials: true` 等于全站开放带凭据跨域

**文件**：`backend/src/main.ts:31`

```typescript
app.enableCors({ origin: true, credentials: true });
```

任意站点都能带 Cookie 发起跨域请求。虽然当前走 Bearer token 风险相对低，但响应体可被跨域读，结合任何 JSON 劫持场景都会数据外泄。

**修复**：改为白名单模式，从配置读取允许的 Origin 列表。

---

### P0-7 deploy.sh SSL 引导步骤完全失效，全新服务器无法部署

**文件**：`deploy/deploy.sh:71-83`

`nginx -t` 只测配置不启动服务 + heredoc 在 `-d` 模式不转发 stdin，导致 80 端口无服务，certbot webroot 验证必然失败，部署链路断裂。

**修复**：改用 certbot `--standalone` 模式，或为无证书场景提供降级 nginx 配置。

---

### P0-8 扫码 App keystore 密码明文硬编码在源码中

**文件**：`scan-app-android/app/build.gradle.kts:42-43`

```kotlin
storePassword = "canteen-internal-2026"
keyPassword = "canteen-internal-2026"
```

keystore 文件和密码同时存在于项目目录中（虽然 keystore 被 .gitignore 排除，但密码已在 git commit `6cf4c3b` 中公开）。任何人可冒签应用。

**修复**：密码移至 `keystore.properties`（已 gitignore），如已泄露重新生成 keystore。

---

### P0-9 管理后台 token 存 localStorage，存在 XSS 窃取风险

**文件**：`admin-web/src/utils/request.js:12-22`

```javascript
const TOKEN_KEY = 'admin_token';
localStorage.setItem(TOKEN_KEY, t);
```

localStorage 可被 JS 直接读取，一旦存在 XSS 漏洞（如富文本渲染、第三方依赖注入），token 立刻被窃取。管理后台 token 有 super 权限，损失巨大。

**修复**：改用 HttpOnly Cookie（需后端配合），或至少加 CSP 策略降低 XSS 风险。

## 三、重点 P1 详解

### P1-1 员工绑定竞态（check-then-act 非原子）

`auth.service.ts:161-206`：先查 `candidate.openid`，再 `save(candidate)`。两个微信用户并发登录同一手机号 → 都读到 openid=null → 都通过校验 → 后者覆盖前者绑定。两个 token 都带 token_version=N 都可用，DB 只认后者的 openid。

**修复**：条件 UPDATE 原子绑定：
```typescript
const res = await employeeRepo.createQueryBuilder()
  .update(Employee).set({ openid })
  .where('id = :id AND (openid IS NULL OR openid = :oid)', { id, oid: openid })
  .execute();
if (!res.affected) throw BizException.forbidden('已绑定其他微信');
```

### P1-2 时段内次数校验非原子（check-then-act）

`verify.service.ts:449-474`：COUNT 查询后再判断是否超限。两次并发核销可能都通过校验，最终超出限制。`issue()` 的"作废旧码+创建新码"也是非原子的，并发调用可创建多个活跃动态码。

### P1-3 consumptions 表无 DB 级幂等

幂等完全依赖应用层（Redis SETNX + QR status）。数据库唯一约束是最可靠的兜底防线。

**修复**：
```typescript
@Index('uk_qrcode_consumption', ['qrcode_id'], { unique: true })
```

### P1-4 Coroutine 失败永久降级

`redis.service.ts:39`：`retryStrategy: () => null` 意味着首次连接失败后永不重连。网络瞬断即永久失效防重放。

### P1-5 设备接口无限流

`/api/device/verify` 是 `@Public()` 接口，无 IP 限流。可被 DoS（每次请求触发多条 DB 查询）或枚举 token（虽然 48 位 hex 穷举不现实，但 Redis 可被打爆）。

### P1-6 部署层：Redis 无密码 + 镜像浮动 tag + nginx 无安全头

三个部署层问题叠加使内网横向移动和供应链攻击风险上升。

## 六、设计亮点（值得肯定）

| 亮点 | 说明 |
|------|------|
| `token_version` 会话吊销 | 改密/停用/解绑递增版本号，守卫逐请求比对，弥补 JWT 无状态吊销缺口 |
| 设备密钥只存 sha256 | 拖库也无法直接拿到密钥明文 |
| 租户隔离强制点 | companyId 取自 JWT 不取请求参数，TenantGuard + service 层 scope 双层校验 |
| 核销时段校验先于扣减 | 注释明确「时段不满足一次都不能扣」，避免「被拒却掉额度」的体验硬伤 |
| 操作日志冗余快照 | operator_name/employee_name 快照，员工离职后审计仍可追溯 |
| Redis SETNX 快速并发拦截 | 在 DB 操作前先占位，避免无效 DB 查询 |
| token_version + 操作日志配合 | 解绑微信时 token_version+1 + 作废二维码 + 记操作日志 |
| 后端容器非 root + tini | 安全基线正确 |
| Android 权限最小化 + allowBackup=false | 移动端安全合规 |

## 八、整体评价

**业务逻辑层**（核销闭环、额度管理、自锁保、租户隔离、操作日志快照）的实现质量**很高**，注释详尽，能看出对并发与边界有充分思考。`token_version` 机制、设备密钥 sha256 存储、`toOperator()` 类型收敛等都是业界最佳实践。

**安全基线层**存在系统性缺陷——核心模式是「配置缺失时静默降级到不安全默认」（JWT 密钥、mock openid、legacy token 都是如此）。这是从「能跑」到「可上生产」的关键差距。

**部署编排**整体结构合理（四服务、健康检查、数据卷、ACME），但 deploy.sh 的 SSL 引导 bug 会导致全新部署失败（当前线上环境是用 `enable-https.sh` 手动签的证书绕过了这个 bug）。

**建议**：先修第一梯队的 5 项（都是小改动），即可达到生产安全基线；第二梯队事务改造工作量约 1-2 天，是核销系统的资金安全底线。
